## Classes

I derived eight classes plus one unclassified. Kinds, not topics: the question was "what sort of thing did the author write down", not "what is it about".

### 1. Verification gaps — the check certified something other than what it was believed to certify

**Test:** an item belongs here if it records a test, control, fixture, harness, gate, mutation run, or comparator that produced a verdict, and the verdict turned out to be about a different question, a different moment, a dead branch, or an input the author never constructed — and the rule is about how to make the check able to fail.

**Members (38):** F2, F3, F12, F52, F53, F56, F57, F58, F59, F60, F61, F62, F63, F64, F65, F66, F67, F68, F69, F71, F72, F73, F75, F78, F84, F85, F94, F101, F113, F114, F120, F130, F135, F143, F150, F155, F157, F158

**Prevention / usability.** Almost every item here ends in a one-line mechanical check the author already knows (`assert n == 1`; run the cell with `-t` alone; `bash -n` the emitted string; run the binary against the real store; name an input that fails the control). What was missing was not knowledge but a place where those checks run without the author remembering. The intervention I would build: a **verification wrapper the seat must go through to report a result** — a single script (owned by whoever owns the harness, invoked by the land command) that, given a test file and an optional mutation, (i) applies the mutation and refuses to run the suite unless the substitution count matches, (ii) runs each new/changed test cell in isolation as well as in the suite, (iii) runs the full gate (`tsc`, `biome`, `bun test`) rather than `bun test` alone, and (iv) for any command whose output is emitted to agents, executes it against the live store and prints the human render into the report. It fires at "I am about to say this is done" — i.e. as a precondition of `READY`/land — and its output is what the seat pastes, so a claim without the wrapper's stamp is visibly unbacked. The router (F52) is the author's own attempt at this as prose; three seats never consulted it, which is the evidence that a prose index does not fire and a tool that refuses to emit a number does.

**Specificity.** The mechanism ("the instrument answered a different question") is one any agent team writing tests will hit. The specific faces are this seat's kind of work — it builds the verification tooling (mutation harnesses, contracts, emitted command strings, dual-audience envelopes), so its checks are checks of checks, and errors compound. Perhaps a third of the members (dual-audience emitter, `uncheckedAgainst` timing, `git archive` domain, spellbook control) are project-specific instances.

**Recurrence.** Two items are recorded twice at file level (F3→F75, F12's sibling-test defect→F114). But the class is internally the most recurrent in the file: the author merged twelve faces into one cluster because they were "one lesson seen from twelve angles", and several single ids carry 3–4 instances (F65 three mutation mechanisms; F71 three instances in one function; F63/F64 a matched pair). So: 2 file-level repeats, ~36 recorded once, with heavy within-item recurrence.

**Prevention / usability.** This is the class the author says is "still costing the team rounds" (the session-10 line failed in three consecutive sessions in a new way each time: comment fix → drafting → import-then-use). Every failure had the same shape: the author classified the act as "not an edit to the shared tree" and the classification was the whole guard. **Test:** an item belongs here if the recorded failure is in something published — a claim, count, identifier, criterion, headline, card note or title, contract clause, or instruction — that was false, unbounded, stale, restated-from-memory, or unfollowable, while the underlying measurement or code was sound; the rule is about what may be said and when.

## Notes

**Readability with no context.** Hard, and slow. Specific reasons:

- **Vocabulary is assumed.** Seats, the wire, the board, cards, lands, the gate, `seams.md`, contracts numbered 3–7 with lettered clauses, rulings R18/R22/R29, `principles.md`, `retro.md`, `uncheckedAgainst`, the vine, spellbook, bounty — none is defined. I inferred most from use (a "land" is a commit to the shared tree; the "wire" is the comms log; a "card" is a board item) but I could be wrong on some, and a curator without the project would have to guess as I did.
- **Order is inverted twice.** The epitaph stack is newest-first (13, 12, 11, 10) and each one scores the ones below it, so the reader meets the verdicts before the lines they judge. The curation notes are oldest-first. The lessons are roughly oldest-first but with session-13 material merged into session-6 bullets. Establishing "what happened in which session" required reading the whole file three times.
- **Emphasis hides structure.** Nearly every sentence is bold, caps, or both, and the ⭐/⚠/🔴 markers are used for "new", "warning", and "severe" without a key. When everything is a headline, nothing is; I had to strip the typography to find the items.
- **Self-reference is dense.** Items cite other items ("this file's (i)", "the clock lesson above", "the coupling lesson below", "session-6 scar") by position, and positions moved as sessions merged entries. Several references I could resolve only by content-matching.
- **Yet each item is unusually well anchored.** Almost every lesson carries a sha, a command, a test name, or a number — and the author distinguishes "pinned" (there is an assertion) from "carded" (there is a work item) from "recorded open". That is what made an inventory possible at all, and it is the part worth preserving in whatever format replaces this.

**Things the questions did not ask about:**

- **The file argues with itself, on purpose.** Every ratio is flagged rather than defended, every merge is listed "so you can judge whether I cheated", every falsifier names what would prove the author wrong. That is a strength for curation (the author has pre-sorted claims by confidence) and a cost for reading (the hedges are as long as the claims).
- **One failure family dominates.** By my count the shared-tree/isolation failure (class 2) is recorded ten times across four sections and three epitaph generations, and the author says it is the one "still costing the team rounds". It is also the one whose fix is structural (worktree or scratch by default) rather than dispositional, and the author found that fix in session 12 (F97). If the curator does one thing with this file, it is to check whether that structural fix was kept.
- **The epitaph mechanism is being audited by its own authors.** F25 records an outside audit: 1 in 9 epitaphs ever shown to fire. The sessions after it score every line. Scored, the session-11 and session-12 lines fire; the session-10 line fails each session; the session-9 line fired and was retired for that. So the trail's own data says a line that names a mechanical act (run a command, use the artifact) fires, and a line that names a disposition (be isolated) does not — which matches the pattern across classes 1–4 in this file.
- **Repeats are mostly deliberate.** Of the 22 flagged repeats, most are the author's own choice to record an incident both in the epitaph (as disposition) and in a lesson (as mechanism), or to keep struck candidates "for the lesson". The author is aware of the cost (F44 explicitly declines to duplicate once) and still does it elsewhere. A curator should treat a repeat as one item with two homes, not as two datapoints.
- **Two items are internally contradictory and say so.** F134 corrects F133 (the code did the opposite of the lesson); F108 corrects a claim the author made about a peer's land. Both are kept in place with the correction attached, per the author's stated rule that a visible correction beats a silent deletion.
- **The sha `d3ac6dd` in F87 is intentionally unresolvable** — the author says so inline so that sha audits do not flag it. Any tool that lints identifiers over this file needs that exemption.
