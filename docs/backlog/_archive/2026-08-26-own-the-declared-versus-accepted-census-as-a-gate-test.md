# Own the declared-versus-accepted census as a gate test

**Added:** 2026-08-26, after running the census once by hand against
[agent-cli-conformance](https://github.com/ichabodcole/agent-cli-conformance)'s
`acc check --recorded-surfaces` reader (kit at `5dbe020`, target at `c010bc5`).
**Related:** [the manifest cluster](2026-08-26-the-manifest-describes-a-surface-we-do-not-have.md) —
this is that item's "what stops the next one" question, answered.

---

## What the check is

Diff **two independent derivations of the same fact**:

- the **manifest**, generated by walking `define.ts` structures;
- the **parser's own rejection string**, produced at runtime by the code that does the accepting —
  `Unknown option '--x'. Valid flags: --channel, --format, …`

Different code paths, different derivations, so the diff is a real differential rather than a
tautology. One inert probe per command path; every probe fails at parse, so no command body runs.

## It has been run once, and it works

25 recorded paths, kit executing nothing below the root:

- **8 `declared-not-accepted`** — `--team` at `info show`, `info env`, `scan`, `feedback`,
  `field-notes`, `migrate`; `--as` at `comms read`, `comms positions`. That is the whole of `DT-2`,
  found mechanically.
- **1 `self-description-not-declared`** — `help` at the root. `DT-6`, with no probe at all.
- **0 `accepted-not-declared`** — no undeclared surface. A real, clean result about anthill.
- **23 of 26 declared paths compared**; 22 of 25 recorded paths enumerate.

## Why we should own it rather than lean on the kit

**The kit can only report the weaker half of what we know.** Its output has to print both readings:

> _either the declaration claims `--team` is valid at `info show` and the enumeration does not name
> it — the enumeration may also be short of a flag the tool does accept_

It says either/or because from outside it cannot tell which side is wrong. **We can.** `--team` at
`info show` is deliberately refused and the manifest is the wrong one. For us it is a defect with a
known direction, so it should fail `bun run check` at commit time rather than appear as evidence in
somebody's report.

It also costs almost nothing and needs no dependency: we already generate the path list from our own
manifest, and the rejection strings are our own. The kit is not required to run it.

## What it catches, and what it does not — read this before scoping

| defect                                  | caught?                                 |
| --------------------------------------- | --------------------------------------- |
| `DT-2` refused flags published as valid | **yes**, all 8                          |
| `DT-6` manifest omits `help`            | **yes**, via self-description           |
| `DT-3` positionals inside `flags`       | **no** — compares names, not containers |
| `DT-9` bare document, no envelope       | **no** — different axis                 |

**One and a half of four.** It compares flag **names** and nothing else — not types, not arity, not
value sets, not output shape.

**And one blind spot it cannot close by construction:** a flag missing from `define.ts` entirely
makes both sides agree and the check pass. A differential between two derivations of one source
cannot see a defect in the source. "Declared versus accepted" sounds like completeness and is not.

**So this does not replace pointing an outside kit at us periodically** — that is the only thing
that reads our surface without sharing our assumptions, which is
[AGENTS.md's own testing rule](../../../AGENTS.md) applied to the manifest.

## What to decide

1. **Test or script?** A `bun test` case that spawns 25 subprocesses costs real gate time. Measured:
   the probes took a few seconds by hand. If that is too slow for every commit, the alternative is a
   script the pre-push hook or CI runs, and the gate stays fast.
2. **What does it assert?** Strictest useful form: **the manifest's flag set for a path equals the
   set that path enumerates.** That fails today on all 8 refused flags — so either it lands
   _after_ the manifest gains a `refused` slot, or it lands now with those 8 pinned as known
   failures and the fix removes them one by one. The second is more honest and gives the fix a
   test to turn green.
3. **Group nodes.** `info`, `comms` and `team` enumerate nothing (no flags of their own), so they
   cannot be compared. Do they get excluded, or does the gap get fixed — see the sibling item below.
4. **Does the emitter get a `refused` field first?** This check and that fix are the same work
   approached from two ends, and doing the fix first makes the test trivially green, which is the
   worse order.
